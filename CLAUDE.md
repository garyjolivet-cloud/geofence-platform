## Development Commands

Run from the **project root** (not from backend/ or frontend/).

```bash
# Start the local Worker dev server (serves HTML + /api/* together)
npx wrangler dev

# Apply all migrations to local D1 (first-time setup) — run every file in
# migrations/ in numeric order; the excerpt below shows the pattern, not
# every file (0003 creates the bot table, 0017 drops it — apply both, in
# order, for the same net result as a fresh install)
npx wrangler d1 execute geofence-db --local --file=migrations/0001_schema.sql
npx wrangler d1 execute geofence-db --local --file=migrations/0002_weather.sql
# ... apply every migrations/000N_*.sql file in order ...
npx wrangler d1 execute geofence-db --local --file=migrations/0017_drop_bots.sql

# Apply migrations to remote D1 (same pattern, --remote)
npx wrangler d1 execute geofence-db --remote --file=migrations/0001_schema.sql

# Deploy to Cloudflare
npx wrangler deploy
```

After starting `npx wrangler dev`, open http://127.0.0.1:8787 in a browser. Keep the wrangler terminal running — it must stay alive to serve the site. Use a second terminal for all other commands.

## Architecture

- **Worker** (`worker.js`): handles `/api/*` routes, falls through to `env.ASSETS` for everything else. Also has a `scheduled()` handler for cron jobs.
- **Friendly URLs**: the Worker maps `/editor` → `fence-editor.html`, `/sim` → `geofence-sim.html`, `/engine` → `geofence-engine.html`, `/dashboard` → `dashboard.html`, `/share` → `share.html`, `/audio` → `audio-bench.html`, `/pipeline` → `pipeline-editor.html`.
- **D1** (`geofence-db`, binding `DB`): stores projects, published bundles, API keys, devices, consent records, events, weather cache, snow history.
- **R2** (`geofence-audio`, binding `AUDIO`): stores audio clips, served via `/api/audio/<key>`. See **Audio Storage** below for the key scheme.
- **AI** (binding `AI`): Cloudflare Workers AI — used for Whisper STT (`/api/transcribe`) and TTS (`/api/tts`).
- **Auth**: master token via `ADMIN_TOKEN` secret. Scoped per-app API keys stored as SHA-256 hashes in D1.
- **Cron**: `"0 * * * *"` (hourly) scrapes Kicking Horse weather into `weather_cache`; `"0 15 * * *"` (8am MST) saves daily snow snapshot to `snow_history`.

## Audio Storage

Audio clips are organized as a **real nested folder tree**, stored in D1 (`audio_folder` + `audio_clip`, `migrations/0019_audio_tree.sql`), fully decoupled from R2 key layout — an R2 key is a **permanent, opaque id** once assigned (`clip/<uuid>.<ext>` for anything uploaded/copied since this migration; legacy pre-migration objects keep whatever path-shaped key they already had, forever). Renaming or moving a folder or clip is purely a D1 metadata update — it never rewrites, copies, or touches the underlying R2 object, regardless of how many clips live in a subtree.

Two scopes, both fully nestable (arbitrary depth):

- **`scope='project'`, `scope_id=<projectId>`**: a project's own clips — recorded/uploaded via `fence-editor.html`'s Audio Palette or Audio Studio. Only ever visible while inside that owning project.
- **`scope='library'`, `scope_id=<orgId>`**: one company's shared clips, reusable across every project/app belonging to that org (same `orgId`/client id used everywhere else — `project.orgId`, `app.orgId`, `user_account.org_id`). Two companies never see each other's library even though rows live in the same tables.

**`frontend/audio-tree.js`** (`window.AudioTree`) is the one shared tree-browser widget behind both surfaces — no per-page reimplementation:
- **Audio Studio** (`/studio`) and the **Fence Editor's Audio Palette** both mount it in **project mode** (`GET /api/audio/tree?project=<id>[&org=<orgId>]`), which returns the project's own tree **plus** its org's Library tree pinned alongside it in the same widget — Library is just a folder node, not a separate tab/button. The Palette mounts it `readOnly:true` (drag-source only; all editing happens in Studio); Studio mounts it read-write. The optional `&org=` override lets the Fence Editor pick a Library via its own "Customer" dropdown even before the project has a persisted `orgId` (a project row doesn't exist in D1 until first Publish, but Record/Upload work before that).
- `AudioTree.mount()` also supports a **library mode** (`GET /api/audio/tree?scope=library&org=<orgId>`, no project tree, just that org's Library as the root) and the backend still serves it — it just has no live caller today. The standalone `/library` page that used to mount it this way was retired (no page ever linked to it after the persistent top-nav rollout, and its only real capability gap vs. Audio Studio — organizing a company's shared clips with no project open — was accepted as out of scope) rather than re-linking a barely-used surface.

**Folder/clip CRUD** (`backend/worker.js`), all authed the same way `/api/audio-list` used to be (`scopeOk`/`libraryScopeOk` against the row's own `scope`/`scope_id`, not a parsed key):
- `POST /api/audio-folder`, `PATCH`/`DELETE /api/audio-folder/:id`, `POST /api/audio-folder/:id/copy` — create/rename+reparent+move/cascade-delete/deep-copy, all any-scope-to-any-scope. A cross-scope folder `PATCH` (`rescopeFolderSubtree` in `worker.js`) bulk-updates every descendant folder's and clip's `scope`/`scope_id` in a couple of statements — no R2 rewrite, no per-row recursion — then reparents just the moved folder's own `parent_id`. Cycle-checking (`wouldCreateCycle`) only applies to same-scope reparents; a cross-scope move can't create one by construction, since the target parent (if any) already lives in a scope disjoint from the folder's own subtree before the move.
- `POST /api/audio-clip` (upload, replaces the old path-driven `PUT`), `PATCH`/`DELETE /api/audio-clip/:id`, `POST /api/audio-clip/:id/copy` — rename/move (including **cross-scope**, since a clip move is one row update)/delete/duplicate (always a true copy — separate R2 object + separate row, per explicit product decision: trimming or deleting one copy must never affect the other).
- `GET /api/audio/:key` (streaming) and the legacy `GET /api/audio-list`, `POST /api/audio/move`, `DELETE /api/audio/folder` are all unchanged and still work during rollout, but are superseded by the tree endpoints above — remove them once every surface is confirmed migrated.

**`POST /api/audio/migrate-legacy`** (master-token only, idempotent) backfills `audio_folder`/`audio_clip` rows from whatever R2 objects already exist, recording each object's **existing** key as-is (never rewritten) — root-level `audio_clip` rows for every project's `<projectId>/` prefix, and one `audio_folder` + `audio_clip` rows for each company's flat `library/<orgId>/[<folder>/]` layout. Safe to re-run (skips any `r2_key` already present) — needed again any time a surface still writing through the legacy `PUT /api/audio/:key` path (e.g. Field Recorder, intentionally untouched by this migration) produces new objects that haven't been backfilled yet.

**Combine** (Audio Studio) lets you select 2+ clips and blend them: a Main sequence (played back to back) plus an optional Background lane (looped/blended underneath at its own volume) get rendered client-side through the same `OfflineAudioContext` → lamejs MP3 pipeline the single-clip Trim tool already uses (`_reenc`/`_reencBlend`), then uploaded as a new clip via `POST /api/audio-clip`. **Trim** on an already-uploaded clip uploads the trimmed bytes as a new clip in the same folder, then deletes the original — there's no "overwrite this key in place" shortcut once keys are opaque/stable.

**Studio sessions** (`studio_session` table, `migrations/0020_studio_sessions.sql`) let a saved Audio Studio timeline be reopened and kept working on later — `frontend/audio-studio.html`'s Save/Save As/Open, `frontend/audio-tree.js`'s `renderSessionRow`/session menu. A session stores which clips are arranged and how (trim points, fades, gain, spatial filter per segment, referencing each clip by its permanent R2 URL) — never audio itself — using the exact same shape as the pre-existing per-project localStorage timeline draft (`serializeTimeline()`/`applyTimelineData()` in `audio-studio.html`, factored out of `persistTimelineDraft()`/`restoreTimelineDraft()` when sessions were added). Sessions live in the same `audio_folder` tree as clips (always `scope='project'` — there's no Library session), so a play's Act/Scene structure is just regular folders with each scene's mix saved as a session inside its own scene folder, right alongside the clips it uses. CRUD: `POST /api/studio-session`, `GET/PATCH/DELETE /api/studio-session/:id`, `POST /api/studio-session/:id/copy` — same auth pattern as clips/folders (`audioScopeAuthOk`).

## Pipeline System (replaced the AI-chat bot system, 2026-07-27)

Zone behavior (what happens on enter/exit/dwell) is authored as a visual drag-and-drop node graph and executed **locally on the visitor's device**, tick-by-tick, alongside the GPS/geofence engine — no server round-trip to decide what fires.

- **`frontend/pipeline-editor.html`** (`/pipeline` route): the canvas. Opened via `?project=<id>&zone=<zoneId>` from the "Edit Pipeline" button in the Fence Editor's per-zone Advanced panel. Hand-rolled vanilla JS/SVG (no framework) — palette of draggable block cards, node drag, port-to-port edge connect, a property panel for the selected node's params. Reads/writes the zone's `pipeline` field via the existing `GET/PUT /api/projects/:id/bundle` — no dedicated pipeline endpoint.
- **`frontend/pipeline-runtime.js`** (`window.PipelineRuntime`): shared block registry (`BLOCKS`) + the local DAG execution engine. Loaded by `geofence-engine.html` (production) and `fence-editor.html` (its built-in test simulator). API mirrors `guidance-bot.js`'s lifecycle: `load(zone, callbacks)` / `tick(zoneId, fix, smoothedPos, {entered,exited,dwellSeconds})` / `unload(zoneId)`. Side effects only via injected callbacks (`sayFn`, `guideStartFn`, `webhookFn`) — never touches DOM/audio directly.
- **Schema**: `zone.pipeline = { v:1, nodes:[{id,type,x,y,params}], edges:[{id,from:{n,p},to:{n,p}}] }`, stored inside the zone object in `published_bundle` — same place `zone.bots` used to live. No new top-level bundle key, no schema migration for `published_bundle` itself (already a JSON blob column).
- **v1 blocks**: `trigger.zone_enter`/`trigger.zone_exit`/`trigger.dwell`, `data.weather`/`data.snow_history`/`data.position`/`data.dwell_time`, `logic.compare`/`logic.and`/`logic.or`, `action.speak`/`action.guide_to_zone`/`action.webhook`. `action.guide_to_zone` is the direct replacement for the old bot-based guidance trigger — it calls the untouched `GuidanceBot.start()`.
- **Offline behavior**: pipeline JSON is already local once a bundle is fetched (same as zones/audio, cached via `sw.js`). `data.weather`/`data.snow_history` fetch on load then refresh on a 5-minute interval, not per GPS tick; a stale/missing fetch just leaves those output ports `null`, and `logic.compare` treats `null` as "not met" — so a weather-gated branch silently doesn't fire offline while everything else keeps working.
- **Not in scope**: device-sensor blocks (accelerometer/barometer) — nothing in this codebase reads either sensor today, only `geolocation.watchPosition`'s lat/lon/speed/heading/accuracy.

## Ridge Quest — what counts as "skied a corridor" (run verification, 2026-09-21)

A corridor is credited only when `QGeo.evaluateTraversal()` (`ridge-quest.html`) verifies an **ordered end-to-end pass** of its centreline — not when a track merely enters its band. The old rule ("track within halfWidth+15 m of >= 50% of sample points, band entered and exited once") is gone. Field report: skiing *across* chutes logged them as skied. **Root cause, from prod `quest_run` + `corridor` rows:** most Kicking Horse chutes are short, *wide* blobs (After Pride 75 m x 111 m, Alley 17 50 x 171, South End Dump Run 50 x 161; 46 of 70 run/chute corridors are < 250 m long), so a tolerance of halfWidth+15 m (40-52 m) put every sample point within reach of any track through the middle -> 100% "coverage" -> full authored descent, in 8-24 s. Three chutes logged inside one minute.

A pass must, in order (all constants in `QUEST_TUNING` "Full-run verification"): (1) **start zone -> far end zone**, on the corridor, in order (`ENDPOINT_ZONE_M` 40 m, capped at 25% of length) — top-first is a "down" pass, bottom-first "up"; (2) **>= 80% bin coverage** (`COVER_BIN_M` 20 m), teleport-proof (progress along the line must be explainable by `MAX_ALONG_SPEED_MPS` x dt); (3) **stay on it** (off-route time share, deepest back-slide); (4) **head along it** (movement bearing vs the corridor's local bearing); (5) **plausible time/speed**; (6) **elevation** — measured altitude change must match the authored `descentM` on run/chute/lift corridors with >= 60 m of authored descent (skipped, never failed, when altitude is missing/unreliable). "On the corridor" tolerance is the fix's own accuracy clamped to 8-20 m, and capped at ~8% of the corridor's length so short corridors stay strict (`QGeo.fixTol`). Fixes with accuracy > 35 m are ignored.

**Classification after verification** (`_classifyAndLog`): direction now comes from the verified pass order, not nearest-endpoint. A chute *descended* is ski at any pace (>= 0.7 m/s); a chute *ascended* is a hike (it used to be ski either way). Lift = ascending a lift corridor at >= 1.8 m/s. Hike > 5 m/s is rejected ("too fast to be on foot"), as is any pass that lies mostly (`LIFT_OVERLAP_FRAC`) inside a lift corridor's band — the gondola-over-a-run case. **That lift-band rejection was hike-and-ascending-only until 2026-09-23**, when a field report showed riding the gondola up credited the runs *underneath* as **skied**: pass direction comes purely from corridor geometry (which end zone was reached first), so a run whose "top" end the gondola reaches first reads as a DOWN pass, takes the ski branch at gondola speed, and slipped past the hike-only guard — and with no usable GPS altitude the elevation check is *skipped, never failed*, so nothing else caught it. It now also fires for **any** activity/direction whenever `trip.elevChecked` is false. It deliberately does NOT fire when `elevChecked` is true: real altitude evidence of a genuine descent beats this 2D overlap test, so a run legitimately skied directly under a gondola still scores on a device with usable altitude (both directions are covered by `tests/quest-corridor-detection.test.js`). Like Corridor Guard's lift suppression, this only works if the resort's lift/gondola line is authored as its own `runType:"lift"` corridor — with none recorded there is nothing to test against and it cannot fire. xcski >= 0.6, drive >= 2.5 m/s. `distanceM` (bike/xcski/drive points) is capped at 1.25 x the corridor length.
**Gondola guard band (2026-09-24).** The live Kicking Horse gondola ("Golden Eagle Express Gondi", `runType:"lift"`, 3.2 km, 10 m wide, base→top within 3–7 m of the base/top zones, bundle v179) IS authored. Simulated with the real geometry: a ride was only recognised (≥ `LIFT_OVERLAP_FRAC` 0.6 of fixes in the lift band) up to ~4 m GPS noise (40 % at 6 m, 0 % at 8 m+), because the bare 10 m band is narrower than a phone's real mountain accuracy. `QUEST_TUNING.LIFT_BAND_EXTRA_M = 5` widens the test by 5 m each side: every simulated ride is caught up to 10 m noise. Cost: a run right beside a chairlift (Ridemption Ridge Speedway beside Stairway Chair, 65 % of it within 10 m) is wrongly rejected ~15 % of the time at 4 m noise — only when the phone has no usable altitude (real altitude still overrides the 2D test). Chutes near the gondola (Alley 17, South End Dump Run, …) are unaffected. Pinned both ways in `tests/quest-corridor-detection.test.js` (a ride 8 m off the line is a lift ride; a run 25 m away still scores).

**`_tick` is now two independent things:** the 3 m narration band (speech only, unchanged) and a **run recorder** (`st.rec`) that records everything within halfWidth+40 m (decimated), probes `_classifyAndLog(..., false)` the moment a far end zone is reached having visited the other (a run logs on arrival — not when the player later leaves), and runs one final `(..., true)` check when the player leaves, which is the only time a failure is explained via `onCoverage(name, pct, false, reason)` (and only if >= 40% was covered, so a plain traverse stays silent). `cooldownUntil` is set only after a logged run; the narration band has its own `narrCooldownUntil` so band flicker can never drop recorder fixes. Tests: `tests/quest-corridor-detection.test.js` (99 assertions; tracks are *generated* by walking a real path at a real speed — the old fixtures fed impossible tracks, e.g. 1.1 km in 2 s, which is why nothing caught this).

**Known limits / follow-ups:** all thresholds are unmeasured starting points — field-test for false *negatives* (a corridor authored longer than the real run, GPS drift on a 4 m chute). The server still trusts the client's run (`POST /api/quest-runs` does no re-validation; same platform-wide trust model). Two **overlapping wide corridors** (adjacent chutes whose bands overlap) used to both credit from one descent. **Fixed 2026-10-03 — one descent, one chute:** `_classifyAndLog` now ends in `_offerPass`; verified passes of different non-lift corridors that overlap in time by at least half the shorter (`passesOverlap`) are tie-broken by `QGeo.meanOffsetM` (mean distance of the pass's fixes from each centreline) — only the best fit is logged, the others report "not counted, you were on X" (Home + `RUN not counted` guard-log line). A pass logs at once unless another chute/run is mid-recording (`_rivalRecording`: its recorder has seen an end zone), in which case it waits up to `PASS_SETTLE_MS` (15 s); `_settlePasses` runs every fix, on a timer and on `stop()` (force). A pass overlapping one already logged is never logged too. 12 pairs on the live KH map could double-log before (e.g. Legs Right/Left, Darwin 2/3, 140/141). Tests: `tests/quest-one-descent-one-chute.test.js`. A run corridor authored bottom->top reads as an "up" pass and is now *rejected* with an elevation reason instead of silently scoring as a hike.

## Guidance Bot (`frontend/guidance-bot.js`)

Standalone IIFE module exposing `window.GuidanceBot`. Phone-in-pocket precision positioning — all instructions relative (turn left/right, bear, slow down), no compass directions.

**Zone fields added for guidance:**

| Field | Type | Default | Purpose |
|-------|------|---------|---------|
| `bearingDeg` | `number` | `90` | Direction visitor should face on arrival (0–359°); amber arrow always shown on map |
| `isHazard` | `boolean` | `false` | Marks zone as a routing obstacle (renders red on map) |

**Two phases:**
1. `navigate` — guides to within 8m of target zone center
2. `align` — tells visitor to face `bearingDeg` using GPS travel heading

**Direction instructions** use a state machine with 10° hysteresis: STRAIGHT / BEAR / TURN / AROUND. Heading source is GPS travel heading only (phone in pocket — device compass unreliable). Circular EMA (α=0.15) smooths heading.

**Hazard avoidance**: Turf.js (lazy CDN load) buffers hazard zones 15m, uses convex-hull tangent waypoints (proper geometric tangent — path to waypoint is guaranteed clear). Re-checks only when `_waypointQueue` is empty to avoid overwriting an in-progress bypass. Graceful degradation if offline.

**API:**
```js
GuidanceBot.start({ targetZone, allZones, sayFn, onComplete, onInstruction })
GuidanceBot.update(fix)  // { lat, lon, speed, headingTravel, acc, t }
GuidanceBot.stop()
GuidanceBot.active       // boolean
GuidanceBot.phase        // 'navigate' | 'align' | 'done' | null
GuidanceBot.targetBearing // current arrow bearing (toward waypoint in navigate, bearingDeg in align)
```

**TTS chain** (both engine and editor simulator): Kokoro neural (82M ONNX, browser-cached) → Workers AI speecht5_tts → browser speechSynthesis fallback.

**Fence editor map visuals:**
- Hazard zones render red (`#ff2f4e`) instead of coral
- Amber solid line + draggable tip handle shows `bearingDeg` from zone center (default 90°)
- Blue dotted ring shows `audioM` fade distance
- Orange dotted ring shows `broadcastRadiusM` (tracker circles only)
- Green arrow on sim avatar points toward current waypoint/target during guidance

## Geofence Trigger Engine — Position Smoothing (EKF since 2026-08-07)

The enter/exit trigger state machine (`Geofencer` in `frontend/geofence-engine.html`, mirrored identically in `frontend/geofence-sim.html` and `frontend/fence-editor.html`'s Test Mode) decides zone entry/exit from a **smoothed** GPS position, not the raw fix — raw GPS jitter would otherwise cause spurious enter/exit flicker.

Smoothing is done by a real shared module, **`frontend/kalman-filter.js`** (`window.GPSFilter`), loaded by all three files — this replaced the older speed-adaptive dual-EMA `Smoother`/`SimSmoother`/`makeSimSmoother()` (deleted entirely from all three copies). It's a true Extended Kalman Filter in geographic coordinates: state `[lat, lon, v_north, v_east]`, Jacobian re-linearized every step, measurement noise weighted by `fix.acc` (the old EMA ignored GPS accuracy entirely), and a self-scaling normalized-innovation-squared outlier gate (structurally replaces the old hardcoded speed-based spike-reject clamp, which was the root cause of a real "stuck at 0 above 90 km/h" bug and had already drifted between different values across the three old copies within the same week). API: `GPSFilter.push(fix)` / `GPSFilter.reset()`. Permanent regression tests live in `tests/kalman-filter.test.js` and `tests/gpsfilter-trigger-comparison.test.js` (run with `node --test tests/`) — re-run these before trusting any future change to this file.

If trigger behavior ever regresses again (stops staying "active" past their radius, new stops failing to fire, speed readings sticking at 0), check this module first — and check all **three call sites** (`geofence-engine.html`, `geofence-sim.html`, `fence-editor.html`), since the *smoothing* logic is now shared but the surrounding `Geofencer`/`TUNING`/`SIM_TUNING` trigger-detection code around it is still a deliberate "verbatim mirror," duplicated three times (real extraction is still pending, tracked as future work in `geofence-sim.html`'s own header comment).

## Corridor Guard (`frontend/chute-guard.js`) — polled architecture, and the raw-vs-smoothed position trap

"Corridor Guard" (`window.ChuteGuard`, UI-labeled "Corridor Guard," internal identifiers still `chute*`/`ChuteGuard` on purpose — see the D1 column and the ~40 call sites this would touch to rename) watches a tracked player against corridor geofences and plays a tone when they've drifted outside the width band. Loaded by `ridge-quest.html`, `geofence-engine.html`, `geofence-sim.html`, and `fence-editor.html`'s Test Mode. A 2026-09-19/20 debugging saga (many rounds, each one looking like a fresh bug) converged on four durable lessons worth knowing before touching this file again.

**1. Event-sourced alarms lose events; polled ones can't.** Every early version started/stopped the tone from `onWarn`/`onClear`/`onDisengage` **events** — and kept finding new ways one of those three could silently fail to fire once (an engaged-gate flicker, wandering past `maxRelevantM`, a stalled sim defeating a time-based check). `ChuteGuard.getActiveAlarm()` replaced that: a stateless, pull-based query of "should the alarm be on right now," called on a host-owned ~200ms timer (plus eagerly after every real tick) and force-applied unconditionally every time — same shape a real automotive lane-departure system uses. Nothing is edge-triggered, so nothing can be silently missed; a lost cycle just gets the right answer on the next one. `onWarn`/`onClear`/`onDisengage` still fire for hosts that only want log/toast text, but are no longer the source of truth for the tone itself.

**2. Test Mode's mouse-drag is not like real GPS jitter — don't feed it the EKF-smoothed position.** `frontend/kalman-filter.js`'s `GPSFilter` (see the Position Smoothing section above) exists to reject *real* GPS noise, and does that by being deliberately slow to trust a sudden, surprising jump (inflating measurement noise rather than snapping to it — see `kalman-filter.js`'s own NIS-gate comment). A real walking/skiing/driving person can't teleport, so this is correct there. **A fast mouse drag can** — it's a large, deliberate, sudden position change that looks exactly like a GPS outlier to the filter, so the smoothed position measurably *lags* the real dragged position for a fast throw (confirmed live: an exported Test Mode log showed a drop of an ~1 real second gap between the avatar visually crossing a line and the tone/an "X marks where it went silent" diagnostic marker reacting). `feedSim()` in `fence-editor.html` already had the fix for a *different* system (`SimFencer`, real zone enter/exit) — it builds an unsmoothed `raw = {lat,lon,acc,alt}` specifically to avoid this lag, with a comment explaining why. `ChuteGuard.tick()` was still being fed the smoothed `sm.lat/sm.lon` until this was found and fixed (`2589120`) to use `raw` too. **If a future Test-Mode-only system (in `fence-editor.html` or `geofence-sim.html`) needs a live position and "feels laggy" or "reacts late" only under a fast drag, check whether it's reading `sm.*` instead of `raw.*` before assuming anything else is wrong** — `geofence-sim.html` likely has this same latent issue (another mouse-driven test surface using `sm.*`) but hasn't been fixed since no report has traced to it yet.

**3. The distance check has no altitude axis — a co-located lift line is the fix, not device altitude.** Real field test (2026-09-20): the tone fired while the rider was on the gondola, nowhere near a ground-level chute. `ChuteGuard.tick()`'s `fix` is `{lat,lon,acc,speed,t}` — purely 2D — so a lift line running horizontally close to (or over) a chute's centerline, completely normal terrain at a resort, reads as "inside" the chute regardless of how many vertical meters up the rider actually is. Fixed by reusing the lift corridor's own recorded geometry rather than adding a new altitude sensor path: `load()` now also captures `runType:"lift"` zones into a separate `liftCorridors` array (previously discarded outright, since a lift line was already excluded from being *alertable* itself — see the scope note above); `tick()` checks `nearAnyLift()` first and, if the current fix is within `widthM/2 + TUNING.LIFT_SUPPRESS_PAD_M` (25m, deliberately generous) of any lift corridor, clears any already-sounding alarm and skips evaluation entirely for that tick. **Since 2026-10-03 it resets each corridor's whole state, `everInside` included** (riding a lift = you have left every chute): it used to keep `everInside`, so after skiing part of Torpedo Alley, riding onto the gondola line and stepping off 54 m outside the chute, a full-level tone ran for 10 s (Test Mode log). A chute now alarms again only after the rider has been back inside it; pinned by `testLeavingALiftDoesNotResumeAnOldChuteAlarm`. This only works because the lift/gondola line for a given resort is expected to be recorded as its own corridor in the Corridor Library — if a future "false alarm with no plausible ground-level cause" report ever turns up at a spot with **no** recorded lift line to key off, the next real fix is altitude-based gating (thread device GPS altitude through `GPSFilter`/the EKF into `ChuteGuard.tick()`, compare against the corridor's own ground elevation) — deliberately not built now since phone GPS altitude accuracy is usually worse than horizontal, and it needs new plumbing through all four call sites. `currentlyOnLift` is computed and cached on **every** `tick()` call regardless of whether `corridors` (the alertable set) is empty — a project with only lift corridors and no ski chutes/runs/hikes authored still needs lift detection to work — and exposed via `ChuteGuard.isOnLift()`, so a host can build other lift-aware behavior off the exact same signal instead of a second `nearestOnPath()`-style implementation (see `ridge-quest.html`'s Battery Saver feature below, the first consumer). `getActiveAlarm()`'s dead-reckoning bridge also checks `currentlyOnLift` before extrapolating — without that, DR could re-open the same gondola false alarm moments after `tick()`'s own lift gate just cleared it, purely from a near-zero-elapsed-time prediction off the last real (still-"outside") fix; this was caught by test timing flakiness, not by design, so it's worth remembering if `getActiveAlarm()` is ever restructured again.

**3b. On a lift = being carried UP it, not near it (2026-10-07, Gary: "runs under lifts have to have voice and guards. the lift is canceling out voice").** 34 of Kicking Horse's 137 runs/chutes lie partly inside a lift's band (width/2 + `LIFT_SUPPRESS_PAD_M`; Pioneer, Show Off and Ridemption Ridge Speedway ~100 %, After Pride 58 %), and lesson 3's "near the line" rule silenced both the guard and the voice (`QuestNarration` `ctx.onLift`) on them. `nearAnyLift()` now runs `liftRideStep()` for every lift whose uphill direction is known (`geometry.climbM`/`descentM`, `upAlong`): a ride starts after `LIFT_RIDE_UP_M` 30 m of progress up the line at ≥ `LIFT_RIDE_MIN_MPS` 1.5 m/s within `LIFT_RIDE_WINDOW_S` 30 s, lasts while in the band (a stopped lift stays a ride), and ends on leaving the band or `LIFT_RIDE_DOWN_M` 30 m back down the line. A lift with no elevation keeps the old rule. `liftRide` survives `load()`. Every `isOnLift()` consumer follows (guard reset, voice quiet, Battery Saver, track dropping, Home picture boarding) — no host change. Simulated on the live map through the real module: all 4 lifts detected in 5-7 s at 0/5/10 m noise (97-99 % of the ride); 1233 descents of every run at 3/8/14 m/s gave on-lift fixes on one run only ("Its a 10", a few fixes where it heads up the gondola line). **Known limits:** the first ~30 m of a ride is not yet a ride; riding a lift DOWN is not a ride (voice/guard stay live); `_classifyAndLog`'s separate lift-overlap rejection (run mostly within 10 m of a lift, no usable altitude) is unchanged. Tests: `tests/chute-guard.test.js` (`testRidingALiftVsSkiingUnderIt`). On-mountain unverified.

**4. Battery Saver ("lift mode"), `ridge-quest.html`.** Riders spend hours a day on lifts, during which 3D terrain's continuous per-frame repaint, the device compass, and Chute Guard's 200ms sync poll are all pure waste. `Quest.liftModeActive` (driven by `ChuteGuard.isOnLift()`, debounced `LIFT_MODE_DEBOUNCE_MS`=8s in `_onFix()` to ignore a momentary edge-graze near a lift's base station) gates: `chuteGuardStopSync()`/`chuteGuardStartSync()` globally (works regardless of which screen is open, since Chute Guard's sync poll runs off `Quest.active()`, not screen visibility), and — only while "My map" is open, via the `Quest.onLiftModeChange` callback slot `renderFogMap()` sets — pausing/resuming 3D terrain (`setTerrainOn`, only if it was actually on; resume restores the rider's own `#fogTilt` choice via a separate `userWantsTerrain` var, never forces it on) and `DeviceHeading.stop()/start()`. A 3-way user override (`Quest.liftModeOverride`, `"auto"|"on"|"off"`, persisted `localStorage rq.liftMode`, `#fogBattery` button on "My map") lets a rider force it off (keep full 3D/compass even on a lift) or on (save battery all day regardless of lift proximity) — every override change toasts via the existing `rqToast()`, and every *automatic* engage/disengage toasts too, so the rider always knows why the app's behavior just changed. `Quest._setLiftModeActive(active, reason)` is the single choke point that actually flips the effective state — deliberately kept separate from `setLiftModeOverride()` (which always toasts, since a button tap is a deliberate action) so an auto transition only toasts on a genuine flip.

**4b. Screen sleep — black overlay + wake-lock release (`ridge-quest.html`, 2026-09-23).** Most of a ski day is lift rides and restaurant stops, and the Screen Wake Lock keeps the screen lit through all of it, so `ScreenSleep` (beside `acquireWakeLock`) adds two stages while tracking, both overridden by any touch. **(1)** A full-screen black `#rqSleep` overlay after `SLEEP_TUNING.IDLE_MS` (30 s) untouched, **anywhere while tracking** (runs included since 2026-10-02 — the phone is in a pocket for the whole descent; it used to need lift mode or 5 min stationary); the wake lock is kept, so GPS/tracking/Corridor Guard are untouched. **While dimmed, My map pauses** (`ScreenSleep.onDimChange`, set by `renderFogMap`, nulled on `#fogBack`): `DeviceHeading.stop()` (every compass reading re-rendered the map), avatar moves held (`heldFix`, drawn on wake) and the friend poll stopped; waking restarts the compass unless lift mode is on. Also 2026-10-02: the compass only turns the map past `HEADING_BEARING_DEADBAND_DEG` (2°, wraps across north) and friends are polled every `FRIEND_POLL_MS` (15 s, was 5 s). Toasts (e.g. "Chute N of M") are hidden under the overlay; the Guard tone is audio and unaffected. **(2)** After `STATIONARY_LOCK_MS` (10 min) stationary AND untouched, `releaseWakeLock()` so the phone can really lock — **never while on a lift** (a locked phone suspends JS on iOS and would miss the dismount and the first run), and tracking pauses until the app is reopened (the existing `visibilitychange` handler re-acquires the lock and toasts). A touch *resets the idle clock* rather than latching an override, so someone reading the map on a lift is never blacked out and the screen dims again after 30 s like a normal phone timeout; unlocking the phone counts as a touch, and the overlay auto-hides when lift mode ends or the player moves. Battery Saver "Always Off" (`liftModeOverride==="off"`) disables both stages; "Always On" keeps lift mode permanently on, so it can dim after 30 s idle anywhere. "Stationary" is `stationaryStep()`: an anchor that only moves when a fix lands farther than `max(30 m, that fix's own accuracy)` away, since indoor GPS wanders 30-60 m. The decision logic (`stationaryStep`, `sleepDecision`) is pure and covered by `tests/quest-screen-sleep.test.js`; the overlay DOM is checked by hand. **Known limits:** on an LCD phone (iPhone SE/11/XR, many Android) black pixels save almost nothing since the backlight stays on — stage 2 still helps there; a 10-minute lift queue would release the lock (rare, a touch resets it, one constant to raise); the wake-lock release is inert on browsers where the phone's own auto-lock is "Never" (the screen just stays black). **Real battery numbers are unmeasured** — compare % across a lift ride and a lunch stop with and without it. **Real bug shipped and fixed 2026-09-23:** `noteFix` first passed `QGeo.haversineM` to `stationaryStep` as a bare function; it reads `this.R`, and detached in the page's strict mode `this` is undefined, so it threw from the *second* GPS fix on — killing `Quest._onFix` before the avatar, corridor ticks and Corridor Guard (field report: no blue dot, dead recenter, nothing recorded). The unit tests passed their own distance function and could not see it. Never hand a `QGeo`/`Quest` method around detached — wrap it `(a,b)=>QGeo.haversineM(a,b)` — and the `noteFix` call in `_onFix` is now in a try/catch so this battery nicety can never take tracking down again (regression test runs the real `noteFix` with the real `QGeo` in strict mode).

**4c. Auto-orientation: the map follows the phone's compass AND tilt (`ridge-quest.html` "My map", tilt added 2026-09-23).** Whenever nobody is touching the map, `DeviceHeading.onChange((heading, tilt)=>…)` drives the camera: **bearing** from the compass heading (since 2026-09-19) and **pitch** from the phone's front-back tilt (`pitchForPhoneTilt()`: 0° = phone flat → map straight down, raised toward vertical → tilted view, 1:1 and capped at 60 = MapLibre's default `maxPitch`; `null` when the device gives no tilt, which leaves pitch to the gesture as before). Field report that added it: "tilt is not working when I tilt the phone, only when I touch with two fingers" — it had never been wired up: `device-heading.js` measured tilt, nothing read it, and a comment said pitch was gesture-only. Bearing and pitch go into ONE `map.jumpTo()` (one redraw), pitch only changes past `TILT_PITCH_DEADBAND_DEG` (1.5°) so hand tremor doesn't re-render the map on every event. A finger on the map (`autoOrient` off) always wins, and 2.5 s after the fingers lift `scheduleOrientResume()` eases bearing **and** pitch back to the phone. **Known limits:** `DeviceHeading.tilt` is portrait-only (`beta` swaps meaning with `gamma` in landscape, uncorrected); on iOS the sensor permission needs a gesture, primed by the Start-tracking tap, so without it there is no compass and no tilt; Battery Saver stops `DeviceHeading` on a lift, so the camera holds its last pitch/bearing there; `jumpTo` cancels any in-flight `easeTo` (e.g. the 3D button's pitch-60 ease) on the next sensor event, so with tilt active the phone, not the 3D button, sets the angle. Covered by `tests/quest-tilt-pitch.test.js` (the mapping, plus the real handler run against a fake map); the on-device feel is unverified.
**4d. Lift-mode terrain changes wait for a calm map (2026-09-24).** Field report: "a background task takes over for a few seconds and locks out pan/zoom/tilt". Leading (still unconfirmed on-device) cause: Battery Saver flipping on/off as a run passed near a lift line, each flip calling `setTerrainOn()` = DEM rebuild + a forced `easeTo` pitch under the rider's fingers. Fixes: leaving lift mode needs `LIFT_MODE_EXIT_DEBOUNCE_MS` (20 s) vs 8 s to enter (`liftModeDebounceMs()`); terrain pause/resume goes through `whenMapCalm()` (no pointer down, `!map.isMoving()`, 1.5 s since last touch/wheel, newest request wins); resume eases to the rider's pre-pause pitch, not a forced 60. Covered by `tests/quest-lift-mode-terrain.test.js`. If the lockout persists with 🔋 Off, the cause is elsewhere (3D terrain auto-on after the splash is the next suspect).
**4e. Rider visuals: track, skied stripe, completion toast, sun light (`frontend/ridge-visuals.js`, 2026-09-24).** Rider's rules: **never show or reward speed, never count turns, no day card**; track/stripe must be switchable and light. (1) *Track*: `RQTrack` (persisted per ski day in `rq.track`) is fed from `_onFix` inside try/catch, skipping fixes >40 m accuracy and points <8 m apart. **Lift rides (changed 2026-09-25):** only the RAW `ChuteGuard.isOnLift()` reading goes in, never `liftModeActive` — Battery Saver "Always On" forces lift mode and used to drop the whole day's route. Near-lift fixes are held and only dropped once near a lift for `TRACK.LIFT_CONFIRM_MS` (60 s); leaving sooner puts them back (field log 2026-09-25: walking past the Stairway Chair base fell inside the 30 m lift gate and lost those stretches). The Corridor Guard log now has `TRACKING start`, `BATTERY SAVER set to`, `LIFT MODE on/off (reason)` and a once-a-minute `TRACK points= kept= droppedLift= droppedAcc= heldNearLift= liftMode= battery= nearLift=` line (`Quest._logTrackStats`, `RQTrack.stats()`); drawn as ONE MultiLineString source (`myTrack`, calm aqua) refreshed at most every 15 s and never while a finger is down or the camera moves. (2) *Skied stripe*: layer `runLines-skied` on the existing `runLines` source, driven by feature-state `skied`/`flash` (never `setData`), only for `runType:"chute"`; `Quest.skiedToday` is loaded from `/api/players/:id/chutes/daily` on Home and updated by `Quest._celebrate`. (3) *Completion*: `_celebrate` (after the run POST succeeds) shows "Chute N of M" (or "Chute again"), a 40 ms haptic tap and a 2 s gold flash; isolated in try/catch. (4) *Light*: `applyTimeOfDayLight` sets the winter hillshade's illumination direction from the real sun (anchor `map`), deeper/warmer when the sun is low; only exists in 3D+winter, refreshed every 10 min. (5) One map button, **Skied** (switches BOTH the stripe and the track; RIGHT column, positioned from the measured bottom of the Guard button via ResizeObserver — never a fixed offset; the left column at top 102 is Recenter), both default on, remembered in `rq.showSkied`. Layer order: `orderRideLayers()` must run after every `applyWinter()` (which slots winter layers under the corridor stack). Plain-lines map mode only (same as `drawAllRuns`). Covered by `tests/ridge-visuals.test.js`; the on-device look is unverified (my test browser can't open the real map).
**4f. Fence Editor Test Mode boundary lines are the smooth GuardEdge outline too (2026-09-24).** The pink dashed trigger-boundary lines used to be built per path SEGMENT (`_corridorEdgeSegments`, now deleted), which left gaps/overlaps at every bend, and armed corridors also got tile-fog's kinked `line-offset` yellow lines. Test Mode now builds one smooth outline per corridor with `GuardEdge.featureCollection` (source `runLinesEdge`, each feature carries `guarded`): pink dashed `runLines-edge` for all (look unchanged), solid yellow `runLines-edge-armed` filtered to `guarded:true`; `TileFog.addCorridorLayers(..., {smoothEdges:true})` skips the offset lines (same as `guardByState`). Cosmetic and wrapped in try/catch. Only fence-editor draws boundary lines among the non-Ridge-Quest hosts (engine/sim/gpx-editor/field-recorder/map-paint don't), and Test Mode's run-name labels were deliberately left alone (useful when authoring). Covered by `tests/fence-editor-test-mode-edges.test.js`; the on-device look is unverified.

**5. Test Mode's debug log doesn't scale with corridor count — gate it by distance, not just time.** Real perf report (2026-09-20, Kicking Horse project, ~60 named-run corridors): Test Mode became "very very slow and not functional." `tick()`'s `onDebug` hook (fence-editor.html's diagnostic log panel only — see point 3's `currentlyOnLift` note, this is unrelated to the real alarm) was throttled per-corridor to once per 500ms, but with no distance gate at all — every corridor, however far from the player, got logged every 500ms regardless. Because every corridor's `lastDebugAt` starts at the same value, those 500ms windows land in the *same* tick across all of them, so a project with dozens of corridors produced a burst of dozens of real DOM appends (`simLogEv`'s `createElement`+`prepend`+`toLocaleTimeString`) simultaneously, measured at ~15-20ms for ~50 corridors — enough on its own to blow a 60fps frame budget, recurring every ~500ms for the whole Test Mode session. Fixed by restricting the throttled (non-crossing) branch to corridors with `near.distM<=maxRelevantM` — a crossing event (`outsideNowChanged`) is never gated this way and still always logs, and outsideNow itself already requires being in range, so no real crossing can be missed. Only the "still totally fine, hundreds of meters away" spam is suppressed. If a similar "Test Mode chokes with a lot of stops/corridors" report ever comes up in a different diagnostic-log call site, check for this exact shape first: a per-item time throttle with no relevance/distance gate, all items sharing a synchronized initial throttle window.

**7. Responsive (fused) path — how fast the tone can really be (2026-09-21).** Field report: "2 s is not acceptable." Measured with randomised step-outs (real `kalman-filter.js`, then the real `chute-guard.js` old vs new, 1 Hz fixes with 0.3 s latency, drifting-bias + white GPS noise, Doppler velocity): feeding the guard the **EKF-smoothed** position put the alarm ON a median 1.1-1.75 s (p90 2-2.7 s) after a real exit and **OFF a median 1.6-2.8 s (p90 3.3-5 s)** after a real re-entry. Cause: the EKF's smoothing lag stacked on the 1 Hz fix cadence, plus the old dead reckoning only ran at >= 0.3 m/s with a heading (both from the same smoothed EKF) and needed a further 1 m margin. Fix: a host may pass **`fix.velE`/`fix.velN`** (the phone's own Doppler velocity, low-noise, no smoothing lag) alongside a **raw** position; `chute-guard.js` then fuses them (`fuseFix()`, complementary filter, `RESP_FUSE_K` 0.5, corrected against where the estimate was `RESP_FIX_LATENCY_S` 0.3 s ago) and `getActiveAlarm()` decides the tone from the position extrapolated to *now + `RESP_LEAD_S`* (0.4 s = the known ~0.3 s fix age + ~0.1 s audio start, not a tuned number) with margin `RESP_MARGIN_M` 0. Measured result: ON median ~ -0.1 to -0.75 s (i.e. often *before* the fix that confirms it; p90 0.65-1.2 s), OFF median 0.05-0.45 s (p90 0.85-1.95 s), fewer misses (skiing 30 m chute: 7% -> 1%), **0 false alarms** on a 30 m chute. What remains is the 1 Hz GPS itself — the floor no software removes. **Opt-in and additive:** no velocity in the fix = the fix is used exactly as given, so `geofence-engine.html`, `geofence-sim.html` and `fence-editor.html` Test Mode are unchanged (they still feed the EKF-smoothed position; adopting this there means passing `coords.speed`/`heading` from the raw fix). Ridge Quest's `_onFix` is the first consumer (falls back to the smoothed feed when the browser gives no speed, e.g. the walk simulator). **A corridor narrower than GPS error can't be made steady by any of this:** on the 4 m test chute the edge is only 2.5 m from the centreline, so even a perfect filter alarms 2-10 times a minute from noise alone (old and new alike) — judge responsiveness on a corridor >= ~20-30 m wide, as the real Kicking Horse chutes (50-100 m) are. The guard log now also records `TONE start/level/stop` and `SAY requested/playing/dropped` lines so audio-side latency is visible next to the WARN/CLEAR lines.

**8. Offset cancelling, two tone levels, narration prefetch (2026-09-21, later the same day).** *Offset cancelling* (responsive path only; `applyBias()`, `TUNING.BIAS_*`): while the rider is moving (>= 0.5 m/s), has been inside, and is within (edge + 1 m) of the baseline, the guard learns the slowly-varying signed lateral offset between GPS and the authored centreline (GPS bias + the recorded line's own error) with a 30 s time constant, capped at 3 m, and measures distance from the *corrected* centreline — how car lane systems calibrate against the map while known to be on the road. Reset when the player leaves relevant range. Measured through the real module on a 4 m bike path: false alarms 4.1 -> 1.2/min (good-sky GPS) and 2.4 -> 0.17/min (dual-frequency GPS); no help at poor 3 m GPS (6.7/min either way). **Known limit:** a very slow drift outward is absorbed (bounded by the 3 m cap). The centreline's own recording error matters as much as live GPS error — re-record a narrow path with several averaged passes; even an RTK receiver alarms ~2/min against a phone-recorded 4 m path. *Two tone levels, distance only:* `MAX_LEVEL` 2, `ESCALATE_EXCESS_M` [0, 10], `ESCALATE_AFTER_MS` [0, Infinity] — level 1 (740 Hz steady) = just past the edge, level 2 (1046 Hz, wobble, louder) = 10 m+ past it; time never escalates (a level that appeared exactly 5 s after leaving read as random). All four hosts' tone tables (`CG_TONE`/`CG_ENGINE_TONE`/`CG_SIM_TONE`/`CG_TEST_TONE`) are two entries. Note a *steady* drift outward is still silenced after ~4 s as a deliberate departure, so level 2 mostly appears on a sudden/large excursion. *Narration:* speaks once per approach (`st.narrArmed`, re-armed only beyond the recorder's 40 m hold band) and the TTS audio is prefetched when the player comes within `SAY_PREFETCH_M` (200 m) — the first `/api/tts` fetch measured 1762 ms from entry to sound in the field log.

Related tuning, for context: `ChuteGuard.TUNING.DR_MAX_S`/`DR_CONFIRM_MARGIN_M` implement dead reckoning (extrapolate position from the last real fix's speed+heading, to react ahead of a real phone's ~1s GPS fix rate) — this is a *different* mechanism from the raw-vs-smoothed issue above, and has its own failure mode: with no new real fix at all (not "GPS is slow," but "literally nothing new arrived," e.g. the Test Mode avatar released and not being dragged), DR will extrapolate a stale velocity reading indefinitely up to `DR_MAX_S`, which can phantom-drift the predicted position through a narrow corridor and back out the other side with zero real movement (confirmed live: `STOP_TONE` and the next `START_TONE` both fired with no real tick logged anywhere between them). `DR_CONFIRM_MARGIN_M` (a predicted crossing must clear the edge by a real margin, not just graze zero) is what actually closed this, not the size of `DR_MAX_S` — if this phantom-drift shape reappears in a log (a tone flip with no real position tick between the two events), shrink `DR_MAX_S` first, since a longer window just gives a stale reading more time to travel before the margin catches it.

Per-stop Code Object attach/detach has three call sites in `fence-editor.html` (the floating palette's card-click/`−`-button via `CodeObjects.mount()`'s `onZonesChanged` callback — the one most likely actually used; the map-canvas drag-drop handler; the stop-list-row drag-drop handler) plus one for *global* (project-wide) objects. ## iOS Audio Playback — Two Distinct Restrictions

Two separate iOS Safari/WebKit rules block audio in different ways. Conflating them wastes a fix cycle — confirmed the hard way:

1. **Hardware ring/silent-switch mutes raw `AudioContext` output.** Affects `SpatialVoice`/`AmbientVoice` in `geofence-engine.html` (WebAudio-routed spoken/ambient audio). Fixed in `Audio.unlock()`: play a real, unmuted, looping, silent-WAV `<audio>` **element** once inside a genuine tap — this shifts the page's audio session category so `AudioContext` output is heard regardless of the switch.
2. **Plain `<audio>`-element playback requires a user gesture, per element.** A `new Audio(url)` created later from a non-gesture context (a `geolocation.watchPosition` callback, a timer) does **not** inherit permission just because a *different* element played successfully earlier — only that *same* element stays "activated." Affects `field-recorder.html`'s `playStopAudio()`/`checkProximityAudio()` (GPS-triggered proximity auto-play). Fixed by reusing **one** shared `<audio>` element for all playback (manual taps and auto-play alike) instead of instantiating a fresh one per call.
3. **`speechSynthesis.speak()` has no durable unlock at all on iOS Safari/WebKit (including Chrome-on-iOS, same engine).** Unlike restriction 2's `<audio>` element, there is no "stays activated" state to reuse — confirmed live (2026-08-07): a direct button tap plays fine every time, but the identical `speechSynthesis.speak()` call from `checkProximityAudio`'s `geolocation.watchPosition` callback stayed silent regardless of how recently a real tap had occurred, priming with a dummy utterance on tap, or re-arming on every subsequent tap. There is no known pure-JS fix — don't spend another cycle on unlock tricks for this API specifically. **Fixed by not using `speechSynthesis` for background-triggered speech at all**: `field-recorder.html`'s `playCandidate()`/`sayViaTts()` sends the `say` text to `POST /api/tts` (server-side Workers AI, already used elsewhere as a TTS fallback tier) and plays the returned audio back through the same restriction-2-safe shared `<audio>` element, with `speechSynthesis` kept only as a last-resort fallback if `/api/tts` is unreachable (offline).

**Diagnostic tell**: if a manual tap-triggered play works but an automatic/programmatic one is silent, it's restriction 2 or 3 (gesture requirement) — restriction 1's fix (a separate silent loop) will not help. If everything *looks* like it's playing (event log shows success, gain computed correctly) but nothing is audible regardless of trigger source, ask about the hardware mute switch first (restriction 1). If the silent call specifically is `speechSynthesis.speak()` (not an `<audio>`/WebAudio path), go straight to restriction 3 — don't re-attempt an unlock/re-arm trick for it, generate the audio server-side instead.

## Security Model

**Two token types:**

| Token | Where it lives | What it can do |
|-------|---------------|----------------|
| `ADMIN_TOKEN` | Wrangler secret (never in code) | Everything — master key |
| Scoped API key | D1 `api_key` table (hashed) | Only the scopes you grant: `publish`, `analytics`, `audio` |

**Rule: never use `ADMIN_TOKEN` in a browser.** Use a scoped API key there instead.

**Create a scoped key for browser use:**
```bash
curl -X POST https://geofence-platform.gary-jolivet.workers.dev/api/keys \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"label":"editor-browser","appId":"your-app-id","scopes":["publish"]}'
```

**CORS:** Write/admin endpoints are restricted to `ALLOWED_ORIGIN`. Public read endpoints allow `*`.

**Environment variables** (non-secret, set in `wrangler.jsonc`):
- `ORG_ID` — organisation slug (default: `chase-life`)
- `ALLOWED_ORIGIN` — browser origin allowed on write endpoints

| Protocol | BLE Service | Who uses it |
|----------|-------------|-------------|

- **Never** hardcode or commit Cloudflare account IDs, API tokens, or `ADMIN_TOKEN`.
- Secrets go in `wrangler.jsonc` secret bindings or `.dev.vars` (gitignored) for local dev.
- The `database_id` in `wrangler.jsonc` is not a secret — committing it is fine.
- Secret scanning: `gitleaks` runs in CI (`.github/workflows/secret-scan.yml`) on every push/PR
  to `main`, and locally via `.githooks/pre-commit`. Enable the hook once per clone with
  `git config core.hooksPath .githooks`. Config + public-value allowlist: `.gitleaks.toml`.
  See `SECURITY.md`.
